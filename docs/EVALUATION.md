# Evaluation: the ground truth the team must produce

Chapter 4 of the report is generated by `tools/evaluate.py` from `results/*.json` (`REPORT_RESULTS.md`). Several items
cannot be measured until people label data. This file says exactly what to label, in what format, where to put it, and
which command then produces the numbers. Until the files exist the harness prints "not measured - needs ..." and gives
no number.

Put labels under `evaluation/ground_truth/` (created by you; the harness only reads it):

```
evaluation/ground_truth/
  detection/data.yaml            + images/{val}/ , labels/{val}/       (section 1)
  tracking/gt.txt                MOT 1.1 for data/videos/<clip>.mp4    (section 2)
  violations/events.csv                                                (section 3)
  severity/ratings.csv                                                 (section 4)
  crosscam/ids.csv                                                     (section 6)
  grounding/queries.json                                               (section 7)
```

General rules: label from the video, **before** looking at what the system produced; the held-out sets must never be used
for training or threshold tuning (record in a `README.txt` beside the labels which video, which seconds, who labelled);
label with the tool's default zoom so box edges are tight. Use CVAT (cvat.ai or a local install).

## 1. Detection (X1) - YOLO boxes on a held-out Dhaka set

* What: 300-500 frames from Dhaka footage that `bd_vehicles_best.pt` was **not** trained on (a different day or camera is
  best; if unsure which videos trained it, ask whoever trained it - the repo does not record this). Spread frames over time
  of day and traffic density; take them at least 2 s apart so they are not near-duplicates.
* Classes: the model's 16, in this order (`bd_vehicles_best.pt` names): 0 Bicycle, 1 Bus, 2 Bhotbhoti, 3 Car, 4 CNG,
  5 Easybike, 6 Leguna, 7 Motorbike, 8 MPV, 9 Pedestrian, 10 Pickup, 11 PowerTiller, 12 Rickshaw, 13 Van, 14 Truck, 15 Wheelbarrow.
  Motorbike boxes include the rider(s), matching the training convention. Label every visible vehicle larger than ~20 px;
  skip fully-occluded ones. Classes with fewer than ~20 boxes give a noisy AP: say so in the report.
* How: CVAT task -> rectangles -> export **"YOLO 1.1"**. Arrange as `images/val/*.jpg`, `labels/val/*.txt`, and
  `data.yaml`:
  ```
  path: .            # directory of the yaml
  train: images/val  # required by Ultralytics' loader; unused here, points at the same held-out set
  val: images/val
  names: {0: Bicycle, 1: Bus, 2: Bhotbhoti, 3: Car, 4: CNG, 5: Easybike, 6: Leguna, 7: Motorbike, 8: MPV, 9: Pedestrian,
          10: Pickup, 11: PowerTiller, 12: Rickshaw, 13: Van, 14: Truck, 15: Wheelbarrow}
  ```
* Run: `./.venv/bin/python tools/evaluate.py x1 --data evaluation/ground_truth/detection/data.yaml --imgsz 960`
  (reports AP@0.5 per class both with this harness's VOC all-point definition and Ultralytics' own 101-point value).
* Effort: about 60-90 s per frame with pre-annotation (run the model, import its predictions, correct them), 2-3 min from
  scratch in busy scenes. 400 frames = **8-10 h** with pre-annotation. Two people can split by frame.

## 2. Tracking (X2, DEC-3) - MOT 1.1 tracks

* What: one continuous stretch of **>= 60 s (ideally 120 s)** of a fixed-camera clip, e.g. `data/videos/20261025_092449_side1_1.mp4`
  seconds 0-60. Every vehicle gets one track id for as long as it is visible, including through occlusion (keep the id; mark
  the occluded frames "outside"/"occluded" rather than starting a new track). The harness scores on every 3rd native frame
  (the analysis rate, ~10 fps), so annotating every frame is not required: **annotate every 3rd frame and interpolate** in
  CVAT (track mode, keyframes). Motorbike boxes include the rider.
* Pre-annotation to save time: `tools/evaluate.py x2` writes `results/x2_tracks/bytetrack.txt` and `botsort.txt` in MOT
  format (native frame numbers, 1-based). Import one into CVAT ("MOT 1.1" import) and fix identity errors instead of drawing
  from scratch. Caveat: starting from one tracker's output biases ground truth toward it in ambiguous cases - have a
  second person review the identity breaks, or use a third source for the first pass.
* How: CVAT task on the clip's frames (extract with `ffmpeg -i clip.mp4 -frames ... ` at native rate, or give CVAT the video and
  match frame numbers) -> export **"MOT 1.1"** -> use the `gt/gt.txt` inside as `evaluation/ground_truth/tracking/gt.txt`.
  Frame numbers in gt.txt must be 1-based native frames of the clip.
* Run: `./.venv/bin/python tools/evaluate.py x2 --gt evaluation/ground_truth/tracking/gt.txt --proxy-seconds 60`
  -> MOTA, MOTP, ID switches, fragmentations, IDF1/IDP/IDR for ByteTrack and BoT-SORT on the same detections.
* Effort: 60 s of busy road is ~100-150 vehicle tracks. With keyframes every 3rd frame and pre-annotation: **10-20 h**.
  A calmer 60 s: 5-8 h.

## 3. Violation events (X3) - CSV

One row per true violation, labelled by watching the video **without** the dashboard open. Save as
`evaluation/ground_truth/violations/events.csv` (UTF-8, header required):

```
video,code,start_s,end_s,class,note
20261025_092449_side1_1.mp4,V1,74.5,112.0,Bus,stopped 37 s outside the bus stop
20261025_092449_side1_1.mp4,V2,102.0,102.0,Motorbike,speeding past the sign
```

* `code` = V1..V11 as in SUPERVISION/README; `start_s`/`end_s` = seconds into the video when the violation begins and
  ends (for instantaneous ones such as a wrong-way crossing or a red-light pass, `end_s = start_s`); `class` optional; `video`
  is the file name.
* Be exhaustive over the labelled window: if a stretch is labelled, every violation of every rule in it must be listed
  (including ones the system missed - the whole point). Record the labelled window (e.g. 0-600 s) in `note` of a first row
  or in the README so false alarms per hour can be computed; pass `--duration <seconds>`.
* Run: `./.venv/bin/python tools/evaluate.py x3 --cases <dashboard Export CSV> --match tolerance --tol 3 --duration 600`
  (`--match iou --iou 0.3` for interval overlap). Matching: same code (and same class if both give one), one-to-one.
* Effort: watching at 1x plus pausing: **about 2-3x real time**. 30 min of footage = 1-1.5 h per rule family if you look for
  all rules at once; budget **4-6 h per 30 min** of busy footage. Aim for >= 20 true events per rule you want to report,
  otherwise report counts, not rates.

## 4. Severity ranking (X4) - two raters

Goal: human ordering of how much each violation hurt traffic, to correlate with the impact score (Spearman).

* Sample >= 30 real cases (more is better: with 30 pairs a rho of 0.4 is only just distinguishable from 0), stratified so
  there are several rule codes and a spread of system impact scores (do not pick only extremes; do not show raters the score).
* Each rater independently sees for each case the **same clip** (10 s before to 30 s after, the evidence video) and rates the
  disruption to other traffic on a **1-5 scale** (1 = no effect on anyone else, 3 = a queue or forced slowdown for a few
  vehicles, 5 = blocked the road / major queue). Raters work alone, in random case order, without the system's score or
  priority. Do not rate how illegal it was; rate effect on others.
* Save `evaluation/ground_truth/severity/ratings.csv`: `case_id,rater1,rater2` and a second file of system scores
  `case_id,impact_score` (from the dashboard export).
* Run: `./.venv/bin/python tools/evaluate.py x4 --scores <scores.csv>` -> Spearman rho (against the mean of the raters) with a
  bootstrap interval, permutation p, and the inter-rater rho. If the two raters themselves correlate below ~0.6, the ceiling
  on the score's rho is low: report that.
* Effort: 1.5 min per case per rater: **~1 h each** for 40 cases (+ 1 h to pick and export clips).

## 5. VLM probes (X5)

* Build >= 40 cases from real Dhaka detections: ~20 where the evidence cannot support the finding (crop shows a different
  vehicle class, blur/empty crop, the wrong lane, a stale time) and ~20 well supported. Label each by eye
  `supported | contradicted | insufficient` in a CSV (`case_id,expected,note`). Do not pick the model's easy cases.
* The harness currently summarises the 3 probes in `tools/vlm_probe.py` and does not call the server. Scoring the larger set
  (confusion matrix, false-support rate = P(model says supported | label is contradicted/insufficient)) needs a small runner
  once the set exists; ask for it then.
* Effort: **3-4 h** to assemble and label 40 cases; two raters (1-5 faithfulness of the free-text explanation) add 1 h each for 30.

## 6. Cross-camera (X6)

* Need footage from >= 2 cameras (e.g. the footbridge views) covering the same stretch of time/vehicles, and a table of which
  vehicle is which. For each camera run the pipeline, note each vehicle's local track id and, by eye, assign a global id when
  the same vehicle appears on the other camera (>= 40 vehicles seen on both, plus the vehicles seen on one only):
  `crosscam/ids.csv`: `camera,local_track_id,global_id`.
* For MTMC IDF1 on boxes, the per-camera MOT ground truth (section 2) with ids replaced by the global ids is needed
  (`evaluation.retrieval.mtmc_idf1`). Pair precision/recall needs only `ids.csv` plus the system's global-id assignment.
* Effort: **8-12 h** (matching vehicles across two views is slow: use time of passing and colour/type).

## 7. Grounding / query panel (X7)

* Write >= 30 natural-language queries ("white bus stopping near the bus stop", "motorbike going the wrong way") in
  `grounding/queries.json` as `{"query": "...", "relevant": ["segment_id", ...]}` where the ids come from the segment index
  once WP3 exists; mark which segments truly match by watching them. Include some queries with no match (the panel must
  not invent one) - those are scored separately once the panel exists.
* Run: through `evaluation.retrieval.mrr` / `recall_at_k` (interface already in place).
* Effort: **3-5 h**.

Unit tests of the metrics (hand-computed cases): `./.venv/bin/python -m unittest tests.test_evaluation -v`.

## Metric definitions (so the report can state them)

* **AP@0.5**: VOC2010+ all-point interpolation, IoU 0.5, greedy match by confidence; mAP = mean over classes with GT.
* **MOTA/MOTP/IDSW/Frag**: CLEAR-MOT with IoU >= 0.5 matching and persistence of previous matches; MOTP reported as mean IoU.
* **IDF1/IDP/IDR**: global min-cost bipartite matching of GT and hypothesis trajectories (`lap`).
* **Event P/R/F1**: same code (and class), one-to-one, interval overlap with a 3 s tolerance or temporal IoU >= 0.3.
* **Spearman rho**: Pearson correlation of average ranks (ties handled), from `surveillance.impact.spearman`.
* **MRR / Recall@k**: reciprocal rank of the first relevant item; fraction of queries with a relevant item in the top k.
